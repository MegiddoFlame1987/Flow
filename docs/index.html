The automation (runner)

A runner on your Windows machine moves tasks between steps by itself. A GitHub event wakes it: a comment, a new commit, finished checks. Each time it does at most one thing and goes back to waiting.

Last canary passed 2026-10-11 02:08 UTC on 4d834d4. run

What it does by itself

  • Picks tasks you marked as ready when a writer is free.
  • Prepares the contract. If a product decision is missing, it recommends one and you decide.
  • Starts the writer, then a separate QC session, then records the result.
  • After each action it wakes once more to see if there is a next step.

What it never does

  • approve (ACCEPT) for you
  • merge changes
  • run on a timer
  • poll when nothing changed
  • retry failed actions blindly
  • execute comment text
  • invent requirements
  • apply its own recommendations

Governance: the flow as an AI delivery framework

The same rules that keep AI agents in line on this game are a general pattern for any team that lets AI write production changes: a human approves, AI builds, a different AI checks, a human releases, and everything leaves evidence.

Weak point first: this is one person's project. It has never run in a company, with several approvers, an auditor or a compliance team. The framework column below is the writer's mapping, not a certification.

The pattern in five gates

  1. Intenta human states the outcome
  2. ContractAI writes scope, plan, tests
  3. Approvala human accepts and assigns
  4. Build + verifyone AI builds, another checks
  5. Releasea human tests and merges

What a company would still need

  • Enforcement depends on agent obedience

    Validators check declarations, not behaviour. Schema 5 said so explicitly (runtime_obedience_is_machine_provable = false); schema 6 dropped the key, not the limit.

  • Single human approver

    Every gate is one person. A company needs roles, delegation and approver rotation.

  • Identity is a GitHub login

    No SSO, no per-user roles beyond the Product Owner ID check in po-playtest.

  • Evidence lives in PR comments

    No retention policy, no export to an audit store, no tamper evidence beyond GitHub history.

    V3 had 6,867 lines of production process code and stalled game work for days. Schema 6 cut it to 1,456 and capped it at 2,500 (see History).

What V3 and its retreat teach about the product

Kept the system safe

The writer refused to break a rule ("do not alter policy") even when its own contract asked for it. Nothing unapproved reached main.

Stopped delivery

That refusal, plus the model/effort defect, left game work waiting from 13 Oct until the retreat merged on 21 Oct. Safety and throughput pull against each other.

The fix was subtraction

Schema 6 kept the gates and removed the machinery: 357 → 81 policy lines, 6,867 → 1,456 lines of process code, and a budget so it cannot grow back unnoticed.

What to sell, if anything

Not the code: the contract format, the gate sequence and the evidence rules. Those transfer between companies; runners and adapters do not.
